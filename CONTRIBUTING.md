# Contributing

Thank you for helping improve the Research Software Guidelines. Contributions can range
from fixing a typo to writing a new section. This document covers how the site is
built and the conventions to follow so changes stay consistent.

Where practical, this repository follows the practices the guide itself
recommends: see [Documentation & community](docs/best-practices/documentation-community.md)
and [Project identity & people](docs/best-practices/identity.md).

## Ways to contribute

- **Open an issue** for a correction, a suggestion, or a problem with the site.
  Use the issue templates so the maintainers get the details they need.
- **Open a pull request** for a concrete change. For anything large or structural
  (a new chapter, reorganizing the nav, changing the build), open an issue first
  so the approach can be agreed before you invest the effort.

## Development setup

```bash
git clone https://github.com/LUMC-DCC/rs-guidelines.git
cd rs-guidelines
make install
```

`make` on its own lists every available task.

Dependencies are managed with [Poetry](https://python-poetry.org/); `poetry.lock`
pins the exact versions CI uses, so install from it rather than upgrading
packages ad hoc. To change a dependency, edit `pyproject.toml`, run
`poetry lock`, and commit the updated lock file.

Preview the site locally (usually at http://127.0.0.1:8000/rs-guidelines/):

```bash
make serve
```

Zensical serves the **staged** copy in `build/docs`, not `docs/` itself. So
after editing a page, run `make stage` in another shell to see the change -
the server notices the restaged files and reloads on its own. Leave
`make serve` running; only `make stage` needs repeating.

Before opening a PR, confirm a clean strict build - this is the exact
sequence CI runs:

```bash
make build
```

## How the site is built

- **[Zensical](https://zensical.org/)** renders the Markdown into the static
  site. It builds from `build/docs` - a generated copy of `docs/` - never from
  `docs/` directly, so **edit `docs/`, never `build/`**.
- Navigation is the **`nav`** list in [`zensical.toml`](zensical.toml). To add
  or reorder pages, edit that list; a page not listed there will not appear in
  the nav.
- **Single-sourced reference data** is injected at build time (see below).
  Please verify you understand this before editing reference data.

### The `tools/` directory

The build logic is split deliberately:

- [`tools/`](tools) holds the actual logic and **imports nothing from the site
  generator** - `refdata.py` (the page transforms) and `permalinks.py` (the
  redirect stubs).
- [`tools/prepare.py`](tools/prepare.py) applies them, staging a copy of
  `docs/` into `build/docs` for the generator to build.

Keep it that way. This split is what made the move off MkDocs cheap, and it
keeps the guide's content independent of whichever generator renders it.
**Put new build logic in `tools/`.**

### Single-sourced reference data

Some data lives in one place and flows into the pages automatically. Edit the
source and the change applies everywhere it is used. Never copy these values
inline.

| What | Source (edit here) | How it reaches the pages |
|---|---|---|
| Abbreviations | [`docs/resources/abbreviations.md`](docs/resources/abbreviations.md) | dotted-underline tooltips on every page (`tools/refdata.py`) |
| LUMC contacts | [`docs/resources/contacts.md`](docs/resources/contacts.md) | a `{{token}}` (e.g. `{{rsd}}`) expands to the linked contact inline (`tools/refdata.py`) |
| Organizations | [`docs/resources/organizations.md`](docs/resources/organizations.md) | one flat table (with a `Category` column) → categorized page (`tools/refdata.py`) |

**Paths in raw HTML** (for example the `<video>` embed in
`docs/smp/sciwiz.md`) are resolved **relative to the source file**, exactly
like Markdown links - so an asset in `docs/assets/` is `../assets/...` from a
page in `docs/smp/`. Do not write URL-relative paths there.

Other one-off inline links stay inline in the page they belong to.
Please centralize data that is *repeated across many pages* or needs *consistent structure*.

### Stable links

External tools (e.g., the SMP template) link into the guide through stable
`/go/<slug>/` URLs, so their links do not break when a heading is renamed or a
page moves. Those URLs are defined in [`permalinks.yml`](permalinks.yml) and
generated by `tools/permalinks.py`, which runs after the build. When a linked
section changes its title or location, update that section's `target` in
`permalinks.yml`, so the external link never changes. The `--strict` run in CI
fails if a target no longer resolves.

## Making a change

1. Branch from `main` (`main` is the deployed branch, pushes to it publish the
   site via [`.github/workflows/docs.yml`](.github/workflows/docs.yml)).
2. Make your change; keep one focused change per PR.
3. Run `make build` and confirm it passes.
4. Open a pull request into `main`. The PR template's checklist covers the basics;
   CI runs a [link check](.github/workflows/links.yml) on the built site.
5. A maintainer reviews and merges. Merging to `main` deploys automatically.

Commit messages: short, imperative, and scoped (e.g., "fix broken link in risks").
